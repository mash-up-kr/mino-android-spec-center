# 🎨 디자이너 사용 가이드

디자이너는 **spec 컨펌 게이트**를 담당합니다. 검토 중인 스펙을 유저 플로우 단위로 확인하고 **승인 / 반려**로 파이프라인을 통과시킵니다.
PR·이후 구현 단계(plan·task)에는 관여하지 않습니다. 개발자용 가이드는 [DEVELOPER.md](DEVELOPER.md)를 참고하세요.

> 파이프라인 상태 정의·전이 규칙은 [state-machine.md](../design/state-machine.md), 아래 액션 권한은 [firestore.rules](../../firestore.rules)로도 강제됩니다.

---

## 0. 로그인 & 화면 구성

1. 대시보드 접속 → **GitHub 로그인**(팝업).
2. 최초 로그인 시 **역할 선택** → `디자이너`.
3. 화면 구성
   - **상단 KPI** — 그중 **검토중**이 지금 컨펌을 기다리는 스펙 수
   - **좌측 파이프라인 필터** — 상태별 개수. **`검토중`** 필터로 볼 대상만 추립니다.
   - **중앙 목록** — Feature 검색, 상태/버전 컬럼
   - **우측 상세 패널** — 스텝퍼 · 출처(Figma) · 문서 · **검토 액션**
   - 헤더 **`📘 PRD`** 칩 — 상위 문서(제품 전체 기획)를 읽고 **댓글로 논의**하는 공간 → [5장](#5-prd-상위-문서--읽기--논의)

---

## 1. 검토 대기 확인

좌측 필터 **`검토중`** 또는 상단 KPI **검토중**을 눌러 `spec_in_review` 상태의 스펙만 추립니다.
목록에서 대상 Feature를 선택하면 우측에 상세가 열립니다.

## 2. 스펙 검토

상세 패널의 **`📝 스펙 검토`** → 스펙 미리보기(리뷰 모드)가 열립니다.

> **검수 대상은 `spec.md` 하나입니다.** 개발자는 `/mino-spec` 산출물 2개(spec + 품질 체크리스트)를 올리지만, 컨펌 게이트가 걸린 건 spec 뿐입니다. 함께 올라온 **`📋 체크리스트 보기`** 는 개발자가 스스로 돌린 품질 검증 결과라 **읽기 전용**이고, 코멘트나 승인/반려 버튼이 뜨지 않습니다. 문서 섹션의 `체크리스트 PASS · 16/16 통과` 같은 요약은 "이 스펙이 얼마나 여물었는지" 가늠하는 참고 자료로만 보세요.

- 각 유저 플로우의 **Figma 노드 링크**로 원본 화면과 대조합니다. (스펙에는 이미지가 첨부되지 않고 Figma 링크가 단일 출처입니다.)
- 유저 플로우·요구사항 섹션마다 **제목 옆 💬 아이콘으로 인라인 코멘트**를 답니다.
  - 특정 플로우/요구사항(FR·UX)에 정확히 앵커링되어 개발자가 어디를 고쳐야 하는지 명확합니다.
  - 코멘트는 **개별 삭제** 가능하고, 한글 입력(IME) 중 Enter로 잘못 등록되지 않도록 가드되어 있습니다.

## 3. 승인 / 반려

미리보기에서 결정합니다.

- **승인** → `spec_approved`. 개발자의 **PR 생성** 잠금이 풀립니다.
- **반려** → `spec_changes_requested`. **코멘트가 1개 이상 있어야** 반려됩니다(무엇을 고칠지 없이 반려 불가).

> 뱃지 의미가 헷갈리면 우측 상단 **`상태 · 배지 안내`**를 여세요 — 상태 · PRD 조치 · 승인 경로 · 문서 종류 뱃지를 한 화면에 모아 설명합니다.

## 3-1. 내가 안 본 승인 — 자체 승인 · 무검토 승인

개발자가 컨펌 없이 승인하는 두 경로가 있습니다. 둘 다 **Design 역할 태그로 사유와 함께 Discord 알림**이 옵니다.

| 뱃지 | 무슨 건인가 | 확인 요령 |
|---|---|---|
| **`자체 승인`** (노란) | 이미 내가 승인한 스펙의 재업로드를 개발자가 **디자인 영향 없음**으로 판단해 재승인 (예: PRD 개정 반영으로 기준 PRD 버전만 갱신) | **버전 스냅샷 → 변경분** diff 로 실제로 무엇이 달라졌는지 확인 |
| **`무검토 승인`** (빨간) | **내가 한 번도 본 적 없는 스펙**이 검토 없이 승인됨 — 화면이 없는 기능 스펙이라는 개발자 판단 | 스펙을 열어 Figma 근거가 정말 없는지, 화면 영향이 없는지 확인 |

- 무검토 승인 건은 상세 스테퍼의 `검토` 단계가 **점선(건너뜀)**으로 표시되고, PR 본문 컨펌 줄도 **미체크**로 남습니다
- 목록 위 **`기능 스펙` 탭**(Figma 근거 없는 스펙만)으로 무검토 승인 대상을 몰아서 훑을 수 있습니다 — 탭마다 건수가 표시됩니다
- 검토가 필요하다고 판단되면 **개발자에게 재컨펌을 요청**하세요 — 대시보드에는 디자이너가 승인을 되돌리는 버튼이 없습니다
- **반려한 스펙은 개발자가 뒤집을 수 없습니다** — 반려는 반드시 수정 후 재검토를 거칩니다

## 4. 보충 코멘트

이미 반려된(`spec_changes_requested`) 스펙에 대해 상태 변경 없이 코멘트만 더 남기고 싶으면 상세의 **`💬 코멘트 추가`**를 사용합니다(decision = comment, 파이프라인 상태는 그대로).

## 5. PRD (상위 문서) — 읽기 + 논의

헤더의 **`📘 PRD v1.2.0 · 💬 3`** 칩을 누르면 제품 전체 기획 문서인 **PRD**가 열립니다. spec 하나하나가 "이 화면을 어떻게 만들까"라면, PRD는 "이 제품이 무엇인가"입니다 — 개별 스펙의 배경을 확인할 때 보세요.

> **PRD는 컨펌 대상이 아닙니다.** 승인/반려 버튼도, 상태도 없습니다. 디자이너에게 PRD는 **읽고 논의하는 문서**입니다. 업로드·개정은 `/mino-prd` 산출물 파일을 가진 개발자만 합니다.

<img src="../images/prd-view.png" alt="PRD 뷰 — 문서 탭과 논의 스레드" width="820">

<sub>※ 위 캡쳐는 개발자 화면이라 `PRD 개정 업로드` 버튼이 보입니다 — 디자이너에게는 이 버튼이 없고 나머지는 같습니다.</sub>

- **문서 탭** — 본문. 섹션 제목 옆 **💬**를 누르면 그 섹션에 앵커된 댓글만 우측 스레드에 추립니다
- **논의 스레드** — **디자이너도 전원과 동등하게 씁니다.** 섹션 앵커 댓글 · 1단 답글 · 마크다운 · 본인 글 수정 · 삭제(순서 보존을 위한 소프트 삭제)
  - `@`를 입력하면 사용자 목록 드롭다운이 뜹니다(↑↓ · Enter/Tab · Esc). **반드시 드롭다운에서 고르세요** — `@민호`처럼 한글을 직접 타이핑하면 멘션으로 인식되지 않아 상대에게 Discord 알림이 가지 않습니다
  - 화면에는 이름으로 보이지만 실제로 삽입되는 건 GitHub 핸들입니다
  - 멘션이 포함된 댓글만 Discord로 알립니다(일반 댓글은 소음이라 보내지 않습니다)
- **버전 이력 탭** — 개정 목록과 임의 두 버전 diff(변경된 섹션 요약 포함). "지난주 기획에서 뭐가 바뀌었지"를 확인할 때
- **연결된 스펙 탭** — 각 spec이 PRD 몇 버전을 기준으로 쓰였는지와 조치 등급(🔴 스펙 재작성 필요 / 🟡 스펙 점검 필요)
  - 검수 중인 스펙 상세에 **🔴 스펙 재작성 필요** 뱃지가 붙어 있으면 그 spec은 **낡은 PRD 기준으로 작성된 것**입니다. 컨펌 전에 개발자에게 `/mino-spec` 재실행을 확인하는 게 좋습니다(대시보드가 막지는 않습니다)
- PRD가 등록·개정되면 **Design 역할도 Discord로 태그**됩니다(등록·MAJOR·MINOR). 알림을 누르면 PRD 뷰가 바로 열립니다

## 상태별 디자이너 액션 (한눈에)

| 상태 | 버튼 | 결과 |
|---|---|---|
| `spec_in_review` | **`📝 스펙 검토`** | 미리보기에서 **승인**(→`spec_approved`) / **반려+코멘트**(→`spec_changes_requested`) |
| `spec_changes_requested` | `💬 코멘트 추가` | 상태 변화 없이 보충 코멘트만 기록 |
| (`자체 승인`·`무검토 승인` 뱃지) | (액션 없음 · Discord 알림으로 인지) | 개발자가 컨펌 없이 승인한 건 — 이견이 있으면 개발자에게 재컨펌 요청 |
| 그 외 상태 | (액션 없음) | 개발자/PR 단계 — 디자이너 관여 없음 |
| (상태 무관) | **`📘 PRD`** | 상위 문서 읽기 + 논의 댓글 — 상시 열려 있음 |

> 승인된 spec은 개발자가 `develop`이 아니라 그 이슈의 **base 브랜치**(`…/base`)로 PR 합니다. 디자이너가 브랜치를 고를 일은 없습니다.

```
        spec_in_review
          │  📝 스펙 검토 (Figma 대조 + 💬 인라인 코멘트)
    ┌─────┴─────┐
  승인          반려 + 코멘트(1개 이상)
    ▼                ▼
spec_approved   spec_changes_requested ──▶ (개발자 수정 후 재요청) ──▶ spec_in_review
 (PR 생성 잠금 해제)     │ 💬 코멘트 추가(상태 유지)
```

> 검토 중(`spec_in_review`)에는 개발자가 spec을 수정할 수 없습니다. 남긴 코멘트는 반려 후 다음 라운드에서 반영됩니다.
> 개발자가 승인 이후 spec을 수정하면 자동 무효화되어 다시 `spec_in_review`로 돌아올 수 있습니다(재검토 시 "지난 검토 이후 변경분" diff 확인 가능).
> 단, 그 수정이 **디자인에 영향이 없다고 개발자가 판단하면** 컨펌 없이 `spec_approved`로 되돌릴 수 있습니다(§3-1 자체 승인) — 사유와 함께 알림이 오고 이력에 남습니다.
> **화면이 없는 기능 스펙**은 아예 검토 요청 없이 승인·PR 까지 갈 수 있습니다(§3-1 무검토 승인) — 이 경우도 사유와 함께 알림이 옵니다.
