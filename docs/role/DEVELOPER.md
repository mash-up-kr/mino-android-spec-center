# 🧑‍💻 개발자 사용 가이드

개발자는 스펙을 **작성·업로드**하고, 디자이너 컨펌을 거쳐 **spec PR까지 배출**하는 주체입니다.
디자이너용 가이드는 [DESIGNER.md](DESIGNER.md)를 참고하세요.

> 파이프라인 상태 정의·전이 규칙은 [state-machine.md](../design/state-machine.md), 아래 액션 권한은 [firestore.rules](../../firestore.rules)로도 강제됩니다.

## 0. 로그인 & 화면 구성

1. 대시보드 접속 → **GitHub 로그인**(팝업). 로그인 토큰이 그대로 PR 권한을 가집니다(별도 authorize 없음).
2. 최초 로그인 시 **역할 선택** → `개발자`.
3. 화면 구성
   - **상단 KPI** — 전체 / 작성중 / 검토중 / 승인됨 / PR 열림 / 머지됨
   - **좌측 파이프라인 필터** — 7개 상태별 개수 + 빠른 필터(PR 연결 · **내 담당**)
   - **중앙 목록** — Feature 검색, 상태/버전/PR 컬럼
   - **우측 상세 패널** — 스텝퍼 · **대상 브랜치** · 출처 · 문서 · 버전 스냅샷 · **액션 버튼**
   - 우측 상단 **`스킬 안내`** / **`상태 · 배지 안내`**에서 스킬 사용법과 **모든 뱃지의 의미**(상태 · PRD 조치 · 승인 경로 · 문서 종류) 확인
   - 헤더의 **`📘 PRD v1.2.0 · 💬 3`** 칩 — 상위 문서 PRD 뷰(문서 / 버전 이력 / 연결된 스펙 + 논의 스레드). 미등록이면 `📘 PRD 미등록`으로 뜨고 개발자에게만 보입니다 → [10장](#10-prd-상위-문서)

## 1. 이슈와 base 브랜치 만들기 (로컬, 스펙보다 먼저)

Mino-Android 레포에서 **`/issue`** 를 실행하면 이슈와 함께
`<prefix>/<이슈번호>-<slug>/base` 브랜치가 생성됩니다.

이 브랜치가 이 기능의 **작업 루트**입니다. spec·plan·task 모든 하위 작업이 여기서 분기하고 여기로 머지됩니다
(Mino-Android `docs/conventions/base-branch.md`). 대시보드는 spec 업로드 시 이 브랜치를 조회해 선택지로 보여줍니다.

## 2. 스펙 작성 (로컬)

대시보드 밖, **Mino-Android 레포의 로컬 스킬**로 산출물을 만듭니다. `스킬 안내` 버튼에 실행법이 있습니다.

- `git pull` → **`/mino-spec`** 실행 (기능 설명 + Figma URL) → `docs/specs/{feature}/spec.md` + `quality/spec-checklist.md` 생성
- 품질 체크리스트가 **PASS** 해야 spec 헤더가 `**상태**: CREATED`가 됩니다 — 이게 1차 방어선입니다. 다만 **`DRAFT` 상태나 `[TBD]`가 남은 스펙도 업로드할 수 있습니다**: 확정이 안 된 항목일수록 디자이너 검수에 올려서 답을 받는 게 맞기 때문입니다(경고만 표시됩니다)
- 개정도 같은 스킬로 합니다. **버전(MAJOR/MINOR/PATCH)은 스킬이 사용자 승인 하에 판정**하고 헤더 `**버전**`을 올립니다. 대시보드는 그 값을 읽기만 합니다

## 3. 업로드 + 구조 검증

`+ 새 스펙 업로드` → 첨부 모달. **`/mino-spec` 산출물 2개를 모두 올립니다.**

- **파일 첨부 전용입니다** — 붙여넣기 편집창은 없앴습니다. 문서를 만드는 것도 고치는 것도 로컬 스킬의 일이고, 대시보드는 파일을 그대로 받습니다
- **두 파일을 한 번에 드롭**하면 본문 H1으로 자동 분류됩니다(`# 스펙 명세서:` → spec 슬롯, `# Spec 품질 체크리스트:` → 체크리스트 슬롯). 판별에 실패하면 슬롯의 `파일 선택`으로 직접 지정하세요
- 두 슬롯 모두 채워야 저장됩니다. 오른쪽 프리뷰의 **탭**으로 문서를 전환해 렌더 결과를 확인할 수 있습니다
- **대상 base 브랜치 선택** — `/issue`가 만든 `…/base` 목록이 GitHub에서 조회돼 셀렉트로 뜹니다. 선택하지 않으면 저장할 수 없습니다
- 출처 Figma 링크는 **spec 본문 §1의 `**Figma**:` 줄에서 자동 수집**됩니다(수기 입력란 없음)
- 저장 시 **spec S1–S6 · 체크리스트 C1–C7 구조 검증**([validation.md](../design/validation.md))을 통과해야 생성됩니다. 실패하면 어느 파일의 어느 항목인지 인라인 에러로 뜨고 저장이 막힙니다
- **경고(노란 박스)는 저장을 막지 않습니다** — 상태 `DRAFT`, 미해소 `[TBD]`, 체크리스트 `FAILED`·미체크 항목, 버전 불일치입니다. 그대로 올리고 검수에서 확정하세요
- 통과 시 `status = spec_draft`, 버전은 spec 헤더 `**버전**` 값 그대로
- 기존 스펙 수정 시엔 두 슬롯이 `기존 문서 유지`로 채워져 열립니다. 바꿀 문서만 교체하면 됩니다

> 검증 항목 요약 — **spec**: S1 대상 스펙 경로·제목 · S2 필수 H2 4개 · S3 헤더 메타(상태·버전·날짜·기준 PRD) · S4 FR/UX/SC ID · S5 유저 플로우 구조(진입/완료 조건·TS 표) · S6 템플릿 자리표시자 잔여 0건.
> **체크리스트**: C1 H1 제목 · C2 헤더 메타(작성일·대상 스펙) · C3 상태 어휘 · C4 필수 H2 4개 · C5 체크박스 존재 · C6 자리표시자 잔여 0건.
> 경고(비차단): spec 상태가 `CREATED`가 아님 · `[TBD]` 잔여 · 체크리스트가 `PASS`가 아님 · 미체크 항목 · 체크리스트 대상 버전 불일치(C7).

## 4. 컨펌 요청

`spec_draft`(또는 반려된 `spec_changes_requested`) 상세에서 **`컨펌 요청`** →
`spec_in_review`로 전환되고 **spec이 read-only로 잠깁니다**(검토 중 수정 불가).

> 기준 PRD 버전이 **🔴 스펙 재작성 필요**(MAJOR 뒤짐)이면 확인 다이얼로그가 뜹니다. 막지는 않지만, 대개는 먼저 `/mino-spec`을 재실행하는 게 맞습니다 → [10-3](#10-3-버전-호환--내-spec이-뒤처졌는지)

## 5. 반려 반영 → 재요청

디자이너가 반려하면 `spec_changes_requested`가 됩니다.

- 로컬에서 **`/mino-spec`** 으로 코멘트를 반영해 개정(버전 등급은 스킬이 판정)
- **`spec 수정`**으로 재업로드 → **`컨펌 요청`**으로 재제출

## 6. PR 생성

승인(`spec_approved`)되면 **`PR 생성`** 이 열립니다 →

- `<prefix>/<이슈번호>-<slug>/spec` 브랜치를 **base 브랜치에서 분기**
- `docs/specs/{slug}/spec.md` + `docs/specs/{slug}/quality/spec-checklist.md` 커밋 (plan·이미지 커밋 없음). Contents API 라 파일당 1커밋이므로 커밋 2개가 올라갑니다
- **PR 생성 — base는 `develop`이 아니라 그 이슈의 `…/base` 브랜치** (라벨 `spec`, assignee=본인)
- 상태 `pr_open`, PR 번호/링크 기록

## 7. 이후 단계 (plan / task)

spec PR이 base 브랜치에 머지되면 대시보드의 역할은 끝납니다. **plan·task는 대시보드를 거치지 않고**
같은 base 브랜치 아래에서 **`/mino-plan`** · **`/mino-task`** 로 진행하고, 각 하위 브랜치의 PR도 base 브랜치를 타겟합니다.

## 8. 무효화 (승인/PR 이후 수정)

승인 이후(`spec_approved`/`pr_open`/`merged`)에 **`spec 수정`**을 하면 자동으로:

- `spec_draft`로 **복귀**(재컨펌 필요)
- 열린 PR이 있으면 **자동 close**(무효화 코멘트)
- 헤더 버전이 그대로면 **버전 미변경 경고** — 로컬 `/mino-spec` 개정으로 버전을 올린 뒤 다시 올리세요

## 8-1. 자체 승인 · 무검토 승인 — 디자이너를 거치지 않는 승인

`spec_draft` 상세의 **`⚡ 자체 승인`** / **`⚡ 무검토 승인`** 버튼 하나로, 컨펌 없이 `spec_approved`로 넘어가 PR 생성 잠금이 풀립니다. 쓰이는 상황은 둘입니다.

| | 언제 | 버튼 라벨 |
|---|---|---|
| ① 유지 승인 | 승인 해제된 변경이 **디자인에 영향이 없을 때** (대표적으로 PRD 개정 반영으로 헤더 `**기준 PRD 버전**`만 갱신) | `⚡ 자체 승인` |
| ② 무검토 승인 | **화면이 없는 기능 스펙** — 디자이너가 볼 것이 없어 처음부터 검토가 필요 없을 때 (로깅 이벤트 추가, 내부 캐시 정책 등) | `⚡ 무검토 승인` |

버튼 라벨은 자동으로 갈립니다 — 그 스펙에 **디자이너 승인 이력이 있으면** ①, 없으면 ②입니다.

- **사유 필수** — 입력한 사유는 **컨펌 이력 · spec PR 본문 · Discord 알림** 세 곳에 그대로 남습니다
- **버튼이 보이는 조건** — `spec_draft` + **품질 체크리스트 `PASS`**. 디자이너 승인 이력이 없는 스펙은 추가로 **`[TBD]` 0건**이어야 합니다(확정할 항목이 남았다면 그건 검수 대상입니다). 조건에 걸리면 버튼이 **비활성으로 남고 툴팁에 이유**가 표시됩니다
- **반려됨(`spec_changes_requested`)에서는 쓸 수 없습니다** — 디자이너가 고쳐달라고 한 것을 개발자가 뒤집을 수는 없습니다. 반려는 수정 후 `컨펌 요청`으로만 풀립니다
- **Figma 근거가 있는 스펙**을 무검토 승인하려 하면 한 번 더 확인을 받습니다 — 화면이 딸린 스펙을 실수로 넘기는 걸 막습니다
- 목록·상세에 **`자체 승인`**(노란) 또는 **`무검토 승인`**(빨간) 뱃지가 붙고, 무검토 건은 스테퍼의 `검토` 단계가 **점선(건너뜀)**으로 표시됩니다
- PR 본문 얼라인 체크리스트에는 **미체크**로 남습니다 — 유지 승인은 `- [ ] … 개발자 자체 승인 · 사유: …`, 무검토는 `- [ ] spec 컨펌 없음 — 개발자 무검토 승인(디자이너 검토 이력 없음)`. CODEOWNERS 리뷰어가 알아채도록 한 것입니다
- 디자이너에게는 **Design 역할 태그로 사유와 함께** Discord 알림이 갑니다. 이견이 있으면 재컨펌을 요청받을 수 있습니다

> 판단 기준은 단순합니다 — **디자이너가 봐야 달라지는 게 있는가**. 화면·플로우·요구사항이 실제로 바뀌었다면 `컨펌 요청`을 쓰세요.

> 목록 위 탭 **`전체` / `디자인 스펙` / `기능 스펙`**으로 Figma 근거가 있는 스펙과 없는 스펙을 갈라 볼 수 있습니다(탭마다 건수 표시 · 좌측 상태 필터와 함께 걸립니다). 별도 설정값이 아니라 spec 본문 §1의 `**Figma**:` 줄에서 파생하는 값이고, 개별 스펙의 종류는 상세 패널 헤더 배지로 확인합니다.

## 9. 버전 스냅샷 & 재검토 diff

상세 패널의 **버전 스냅샷**에서 각 버전의 메모를 확인·편집할 수 있고, 재검토 시 **"지난 검토 이후 변경분"** diff를 열어볼 수 있습니다. MAJOR/MINOR/PATCH 뱃지는 직전 스냅샷과의 semver 비교로 표시되는 파생값이며, 버전 값 자체는 `/mino-spec`이 소유합니다.

## 10. PRD (상위 문서)

spec이 "이 화면을 어떻게 만들까"라면 PRD는 "이 제품이 무엇인가"입니다. `/mino-prd` 산출물 `docs/prd/business-context.md` **하나**가 프로젝트 전체의 상위 문서이고, 헤더의 **`📘 PRD`** 칩으로 들어갑니다.

> **PRD는 컨펌 게이트를 타지 않습니다.** 승인/반려도, 상태도 없습니다. 대시보드에서 PRD는 *공유 아카이브 + 논의 공간 + spec 버전 정합 추적기*입니다. **PR도 만들지 않습니다** — PRD 파일은 `/mino-prd`가 워킹트리에 직접 쓰므로 평소 PR 경로로 커밋하세요. 상세 설계는 [prd-track.md](../design/prd-track.md).

### 10-1. 업로드 · 개정 (개발자 한정)

PRD 뷰의 **`PRD 업로드`**(미등록이면 칩 자체가 업로드 유도) → 파일 첨부 슬롯 1개. 업로드·개정 권한은 **개발자만** 갖습니다([firestore.rules](../../firestore.rules)).

- 저장 시 **P1–P7 구조 검증**([prd-track.md](../design/prd-track.md) §3)을 통과해야 합니다
  - **하드 차단**: P1 H1 제목(`# 제품 요구사항 문서 (PRD): {제품명}`) · P2 헤더 **표**(`| **버전** | X.Y.Z |` · 생성일/최종 수정일) · P3 필수 섹션 4개(순서대로) · P4 §2 목표의 `[SYS-00X]`/`[SCR-00X]` · P5 자리표시자 잔여 0건 · P7 **버전 역행**
  - **경고(저장 진행)**: P4-w §2↔§3 항목 대응 불일치 · P6 `TBD:` 잔여
- **`TBD:`를 막지 않는 이유**는 spec의 `DRAFT`·`[TBD]`와 같습니다 — 확정 안 된 정책이야말로 댓글로 논의할 대상입니다. 표기가 spec은 `[TBD]`, PRD는 `TBD:` 접두로 **다르다**는 점만 주의하세요
- 버전은 헤더 표의 `**버전**` 값 그대로 — **버전 소유권은 `/mino-prd` 스킬**입니다(spec과 같은 원칙)
- **저장본과 같은 버전**으로 올리면 확인 후 새 스냅샷 없이 현재 버전 본문만 갱신합니다
- **동시 업로드 보호** — PRD는 하나뿐이라 두 사람이 겹칠 수 있어 낙관적 잠금이 걸려 있습니다. 그 사이 다른 버전이 등록됐으면 저장이 거부되고 "다시 받아 개정하라"고 안내합니다
- 저장 직후 **이 개정으로 확인이 필요한 스펙 목록**(재작성·점검 대상)이 알림창으로 뜨고, 있으면 `연결된 스펙` 탭이 먼저 열립니다

### 10-2. 버전 이력 · diff

`버전 이력` 탭에서 개정 목록(등급 뱃지 · 날짜 · 메모)을 보고, **from/to를 임의로 골라** 비교합니다(spec의 "직전 대비"와 달리 여러 개정을 건너뛴 비교가 가능). diff 상단에 **변경된 섹션 요약**이 먼저 나오므로 긴 문서에서 어디를 볼지 바로 알 수 있습니다. 본문 스냅샷은 불변 기록이라 수정·삭제되지 않습니다.

### 10-3. 버전 호환 — 내 spec이 뒤처졌는지

조인 키는 spec 헤더의 **`**기준 PRD 버전**`** 입니다. 현재 PRD 버전과 비교해 등급이 붙습니다.

| 관계 | 뱃지 | 해야 할 일 |
|---|---|---|
| 동일 | ✅ **PRD 최신** | — |
| MAJOR 뒤짐 | 🔴 **스펙 재작성 필요** | MVP 경계·용어가 바뀜 → **`/mino-spec` 재실행** |
| MINOR 뒤짐 | 🟡 **스펙 점검 필요** | 추가 항목과 주제가 겹치는 spec만 재실행 |
| PATCH 뒤짐 | ⚪️ **영향 없음** | 표현·오타 수준 — 재실행 불필요 |
| spec이 더 높음 | 🟠 **PRD 등록 필요** | 최신 PRD가 대시보드에 없습니다 — 올려주세요 |
| `없음`·파싱 실패 | ⚫️ **기준 PRD 없음** | PRD 이전에 작성된 spec |

> 뱃지 문구는 **"그래서 뭘 해야 하나"** 기준입니다. `스펙 …`으로 시작하면 spec 작성자가, `PRD …`면 PRD를 올릴 사람이 움직일 차례입니다.

- 노출: feature **목록 행 뱃지**(문제 등급만) · 상세 패널 `기준 PRD` 줄 · PRD 뷰 **`연결된 스펙`** 탭(🔴 먼저 정렬) · spec **PR 본문 체크리스트 한 줄**

<img src="../images/prd-compat.png" alt="연결된 스펙 탭 — 재실행 검토 대상" width="820">
- **막지는 않습니다** — 🔴 상태로 `컨펌 요청`을 하면 확인 다이얼로그로 경고만 하고 진행됩니다. "미완성일수록 검수에 올린다"는 원칙([validation.md](../design/validation.md) §1)과 같습니다

### 10-4. 논의 (전원 참여)

PRD 뷰 우측이 논의 스레드입니다. **개발자·디자이너 누구나** 씁니다(업로드만 개발자 한정).

- 본문 섹션 제목 옆 **💬**로 **섹션 앵커** 댓글 — 앵커를 누르면 스레드가 그 섹션으로 필터됩니다. 앵커 없는 전체 댓글도 됩니다
- **1단 답글** · 마크다운 · 본인 글만 수정 · 삭제는 소프트(순서 보존)
- **`@` 자동완성** — `@` 입력 시 사용자 목록 드롭다운(↑↓ · Enter/Tab · Esc). **삽입되는 토큰은 GitHub 핸들**이고 화면에는 이름으로 보입니다. 드롭다운을 거치지 않고 `@민호`처럼 한글을 직접 치면 멘션으로 인식되지 않아 **알림이 가지 않습니다** — 드롭다운에서 고르세요

### 10-5. 알림

`notifyOnPrdWrite` 트리거가 등록·개정을 Discord로 보냅니다.

| 이벤트 | 멘션 | 본문 |
|---|---|---|
| 신규 등록 · **MAJOR** · **MINOR** 개정 | Android + Design + **iOS + Node** | 버전 변화 + **뒤처진 spec 목록** |
| **PATCH** 개정 · 본문 갱신 | 없음 | 버전 변화만 |

> PRD는 제품 전체 문서라 범위가 바뀌면 **4개 역할 전부** 태그합니다. spec 파이프라인 알림(컨펌요청·승인·반려·무효화·머지)은 안드로이드 spec 전용이라 Android/Design 그대로입니다. 동봉되는 뒤처진 spec 목록은 `features` 기준이라 **안드로이드 spec만** 나옵니다.

댓글은 **@멘션이 포함된 것만** 알립니다(일반 댓글은 소음이라 보내지 않음). 알림 클릭 시 `?prd=` 딥링크로 PRD 뷰가 바로 열립니다.

## 상태별 개발자 액션 (한눈에)

| 상태 | 버튼 | 다음 |
|---|---|---|
| `spec_draft` | `spec 수정` · **`컨펌 요청`** · **`⚡ 자체 승인`**(승인 이력 있을 때·사유 필수) | → `spec_in_review` / → `spec_approved` |
| `spec_changes_requested` | `spec 수정` · **`컨펌 요청`** (자체 승인 불가) | → `spec_in_review` |
| `spec_approved` | `spec 수정` · **`PR 생성`** | → `pr_open` |
| `pr_open` | `spec 수정`(→무효화) · `PR 보기` | 웹훅으로 `merged`/`pr_closed` |
| `merged` | `spec 수정`(→무효화) · `PR 보기` | 새 PR 라운드 |

```
/issue → base 브랜치        업로드(S1–S6 + base 선택) → spec_draft ──컨펌요청──▶ spec_in_review
                               ▲                                                    │ 디자이너 검토
                               │  (반려 반영 후 재요청)                              ▼
                               └── spec_changes_requested ◀──반려── ┐   승인 → spec_approved
                                                                         │        │ PR 생성
                                                                         │        ▼
                                                                         │      pr_open ──웹훅──▶ merged / pr_closed
                                                                         │                          │
   승인 이후 spec 수정 = 무효화(→spec_draft 복귀 · PR 자동 close)          머지 후: /mino-plan · /mino-task
                               └─ 디자인 영향이 없으면 ⚡ 자체 승인(사유 필수) ──▶ spec_approved
```
